# Container specification

**Status: normative draft, container version 1.0. Frozen after the Sepolia campaign.** Once
the first byte is published on mainnet this format can be extended (a new minor version may
add record types) but never changed (a decoder for 1.0 must read every 1.x stream correctly,
ignoring what it does not know). Every component of Loculus Eternal is tested against the
golden vectors in `vectors/`, which are generated by
`src/loculus_eternal/format/gen_vectors.py` and never hand-edited.

The words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## The stream

The `LoculusEternal` contract commits to an ordered sequence of Ethereum blobs. This
specification defines how those blobs are read as one byte stream and how that stream is
read as records.

### Chunks and blobs

A blob is 4096 field elements of 32 bytes. Each element carries 31 bytes of data, so that its
value stays below the BLS12-381 scalar field modulus:

```
element = 0x00 ‖ chunk          (1 zero byte, then 31 data bytes, big-endian)
```

A **chunk** is 31 bytes. Chunk *i* of the stream is element *i* mod 4096 of blob ⌊*i* / 4096⌋.
Blobs are numbered from 0 in the order the contract recorded them. The **stream** is the
concatenation of all chunks in order. A blob holds at most 126,976 stream bytes.

A blob that is the last blob of a batch may be partially filled. Its unused elements MUST be
entirely zero. The contract records, per `publish` call, how many elements of the last blob
carry data; a reader that has the stream alone does not need that number, because every
batch declares its own extent (below). Blobs that are not the last blob of a batch MUST be
completely filled.

### Records

Everything in the stream is a **record**:

```
record = uvarint(length) ‖ u8 type ‖ payload
length = 1 + len(payload)
```

`uvarint` is the unsigned little-endian base-128 encoding (LEB128): seven bits per byte, low
group first, high bit set on every byte except the last. Encoders MUST produce the minimal
encoding. Decoders MUST reject an encoding with a redundant trailing zero group, an encoding
longer than ten bytes, or a value above 2⁶⁴ − 1.

Records are self-delimiting and, within a batch, straddle chunk, blob, and transaction
boundaries freely. A reader never needs the blob boundaries except at the start of a batch.

Record types:

| Type | Name | Where | Payload |
|---:|---|---|---|
| `0x01` | `HEADER` | first record of the stream, once | binary, below |
| `0x02` | `BATCH_BEGIN` | first record of a batch (after `HEADER` in batch 0) | binary, below |
| `0x03` | `BODY` | exactly once per batch, after `BATCH_BEGIN` | compressed run of inner records |
| `0x04` | `BATCH_MANIFEST` | last record of a batch | canonical JSON |
| `0x05` | `INDEX` | at most once per batch, between `BODY` and `BATCH_MANIFEST` | `u8 codec ‖ compressed canonical JSON` |
| `0x10` | `ENTRY` | inside a body | canonical JSON |
| `0x11` | `SCHEMA` | inside a body | canonical JSON |
| `0x12` | `TOOLING` | inside a body | binary, below |
| `0x13` | `DICTIONARY` | reserved, inside a body | unused in version 1 |
| `0x14` | `REPROCESSED` | reserved, inside a body | unused in version 1 |

Types `0x01`–`0x0f` are **outer** records (they appear directly in the stream) and
`0x10`–`0x7f` are **inner** records (they appear only inside a decompressed body). A decoder
that meets an inner record type it does not know, within a major version it does know, MUST
skip it by its length and SHOULD report it. A decoder that meets an unknown outer record type
MUST treat the batch as malformed.

### Integers and digests

Binary payloads use fixed-width big-endian unsigned integers (`u8`, `u64`). JSON payloads
are **canonical JSON** as defined by RFC 8785 (JSON Canonicalization Scheme): UTF-8, object
keys sorted by UTF-16 code units, no whitespace, numbers in the shortest round-trip form.
A "digest" is always SHA-256 and, inside JSON, is written as 64 lowercase hexadecimal
characters. The **digest of a record** means the digest of its payload bytes only.

### Codecs

| Codec | Meaning |
|---:|---|
| `0` | raw: the bytes are the content |
| `1` | zstd (RFC 8878) frame, no dictionary |

Encoders SHOULD use codec 1 at compression level 19 for bodies and indexes. Compressed bytes
are not canonical: two zstd implementations may produce different bytes for the same input,
so conformance is defined on **decoded** content. A decoder MUST reject a codec it does not
know. A decoder MUST check that the decompressed length equals the declared uncompressed
length where one is declared.

## Record payloads

### `HEADER`

```
magic                 15 bytes   ASCII "LOCULUS-ETERNAL"
major                 u8         1
minor                 u8         0
chainId               u64        Ethereum chain ID the stream is published on
contract              20 bytes   address of the LoculusEternal instance
schemaId              uvarint(n) ‖ n bytes UTF-8   "pathoplexus"
```

The header is at stream position 0 and appears exactly once. A decoder MUST refuse a stream
whose magic differs or whose `major` it does not implement, and MUST accept any `minor`.
`chainId` and `contract` bind the stream to one deployment so that a stream cannot be
replayed as another instance's data. `schemaId` names the dataset; readers use it to select
the materialisation rules below.

### `BATCH_BEGIN`

```
batch                  u64        batch number, 0 for genesis, then consecutive
firstBlobSeq           u64        sequence number of the blob this batch starts in
previousManifestDigest 32 bytes   digest of the previous BATCH_MANIFEST; all zero for batch 0
codec                  u8         codec of the BODY that follows
uncompressedLength     u64        length of the body after decoding
compressedLength       u64        length of the BODY payload
bodyDigest             32 bytes   digest of the BODY payload (the compressed bytes)
```

A batch MUST begin at chunk 0 of a blob. In batch 0, `HEADER` occupies stream position 0 and
`BATCH_BEGIN` follows it immediately in the same blob.

### `BODY`

The payload is the batch's inner records, concatenated, encoded with `codec`. Its length and
digest MUST equal `compressedLength` and `bodyDigest` from `BATCH_BEGIN`. Inner records in
canonical encoder order are: every `SCHEMA` record (sorted by organism), then every `TOOLING`
record (sorted by path), then every `ENTRY` record sorted by organism, then accession, then
numeric version. Decoders MUST NOT depend on that order.

### `ENTRY`

Canonical JSON of one published accessionVersion:

```json
{
  "organism": "<organism identifier>",
  "metadata": { ... },
  "unalignedNucleotideSequences": { ... },
  "alignedNucleotideSequences": { ... },
  "nucleotideInsertions": { ... },
  "alignedAminoAcidSequences": { ... },
  "aminoAcidInsertions": { ... }
}
```

The six data keys are exactly the backend's released line (see the schema appendix) with the
fields `versionStatus`, `dataUseTerms`, `dataUseTermsRestrictedUntil` and `dataUseTermsUrl`
removed from `metadata`. `metadata.accessionVersion`, `metadata.accession` (string) and
`metadata.version` (integer) MUST be present. An encoder MUST NOT publish the same
`(organism, accessionVersion)` twice; a decoder that meets a duplicate MUST keep the first
occurrence and report the later one.

### `SCHEMA`

Canonical JSON describing the shape of one organism's entries, published in the first batch
that contains entries for that organism and again in any batch where the shape changes:

```json
{
  "organism": "...",
  "metadataFields": ["accession", "accessionVersion", ...],
  "nucleotideSegments": ["main"],
  "genes": ["E", "NS1", ...]
}
```

`metadataFields` lists the keys of `metadata` after projection, sorted. `nucleotideSegments`
lists the keys of `unalignedNucleotideSequences`, sorted. `genes` lists the keys of
`alignedAminoAcidSequences`, sorted.

### `TOOLING`

```
pathLength   uvarint
path         UTF-8, a relative file path with "/" separators
content      the file's bytes
```

Published in the genesis batch and in the first batch after every tagged release: the
container specification, the IPFS profile, the contract specification, and the source of the
Python package, so that a reader holding only the contract address can rebuild the tooling.

### `INDEX`

```
codec     u8
content   canonical JSON, encoded with codec
```

The content lists every accessionVersion published in this batch or before it, with the batch
it was published in:

```json
{
  "batch": 7,
  "entries": {
    "<organism>": {
      "<accession>": [[1, 0], [2, 5]]
    }
  }
}
```

Each accession maps to a list of `[version, batch]` pairs sorted by version. An index is
inclusive of its own batch. **Encoder rule:** an `INDEX` MUST be emitted in a batch when the
sum of `compressedLength` over this batch and every batch after the last one that carried an
index reaches 16,777,216 bytes (16 MiB). An encoder MAY emit one more often. Decoders MUST
accept any placement. A reader that wants the published set reads the most recent `INDEX`
and the bodies of every later batch.

### `BATCH_MANIFEST`

Canonical JSON:

```json
{
  "batch": 7,
  "firstBlobSeq": 310,
  "blobCountAfter": 312,
  "previousManifestDigest": "<64 hex>",
  "bodyDigest": "<64 hex>",
  "hasIndex": true,
  "organisms": {
    "<organism>": {
      "entriesInBatch": 120,
      "entriesTotal": 58779,
      "artifactSha256": "<64 hex>"
    }
  }
}
```

`blobCountAfter` is the contract's `blobCount` once this batch's last blob is recorded, that
is `firstBlobSeq` plus the number of blobs the batch occupies. `previousManifestDigest` and
`bodyDigest` repeat the values from `BATCH_BEGIN`. `organisms` lists every organism with at
least one entry published so far, including organisms with no entries in this batch (with
`entriesInBatch` 0). `artifactSha256` is the **cumulative** digest: the SHA-256 of that
organism's complete materialised file after this batch, as defined below. The manifest is
the last record of the batch; the bytes from its end to the end of the blob are zero.

The **digest of a manifest** (used as the next batch's `previousManifestDigest`) is the
SHA-256 of the manifest record's payload.

## Reading a stream

A decoder proceeds batch by batch:

1. At stream position 0 read `HEADER`; refuse an unknown `major` or wrong magic.
2. Expect `BATCH_BEGIN` next (position 0 of a blob, except batch 0 where it follows the
   header). Check `batch` is the next expected number and `previousManifestDigest` matches
   the digest of the previous manifest (zeros for batch 0).
3. Read `BODY`; check its length and digest; decode it with `codec`; check the decoded length;
   parse the inner records.
4. Optionally read `INDEX`.
5. Read `BATCH_MANIFEST`; check `batch`, `firstBlobSeq`, `previousManifestDigest` and
   `bodyDigest` agree with `BATCH_BEGIN`; check `blobCountAfter` equals `firstBlobSeq` plus
   the number of blobs consumed so far in this batch.
6. Move to chunk 0 of the next blob and repeat from step 2 until the stream ends.

A batch that fails any check, or that ends before its manifest because the stream ends or a
blob is missing, is **torn**. Its records contribute nothing. When a batch is torn and more
blobs follow, the decoder resynchronises: it examines chunk 0 of each following blob in turn
for a `BATCH_BEGIN` whose `batch` equals the expected number and whose
`previousManifestDigest` matches the last good manifest, and resumes there. The blobs skipped
are reported as torn. This is how an interrupted upload whose journal was lost is recovered
from: the publisher simply starts the batch again at the next blob boundary.

A decoder MAY start from the most recent `INDEX` instead of the stream start when it only
needs the published set.

## Materialisation (schema `pathoplexus`)

The materialised output of a stream is one file per organism, named `<organism>.ndjson`,
containing one line per published accessionVersion of that organism. Each line is the exact
`ENTRY` payload bytes followed by a single `0x0a`. Lines are sorted by `metadata.accession`
(byte-wise on the UTF-8 string) and then by `metadata.version` (numerically). The file is a
pure function of the set of entries: no timestamps, counts, or banners. `artifactSha256` in a
manifest is the SHA-256 of this file's bytes after the manifest's batch.

Status fields are not part of an entry. A consumer who needs them derives them from the set:
the highest version of an accession is the latest, lower versions are revised, and a version
whose `metadata.isRevocation` is true revokes the accession.

## Conformance and vectors

`vectors/` holds generated files that every implementation MUST reproduce or accept:

| File | Covers |
|---|---|
| `varint.json` | uvarint encodings and rejected encodings |
| `canonical_json.json` | RFC 8785 output for sample objects |
| `chunks.json` | packing a byte string into elements and blobs, and the last-blob chunk count |
| `batch_raw.json` | a complete genesis batch with codec 0: stream, blobs, manifest, artifacts |
| `batch_zstd.json` | the same batch with codec 1, as a decode vector (compressed bytes are not canonical) |
| `multi_blob.json` | a raw batch spanning several blobs with a partially filled last blob |
| `two_batches_index.json` | two batches, the second carrying an `INDEX` |
| `torn_batch.json` | a complete batch, a torn batch, and the same batch republished at the next blob boundary |

For codec 0 streams two conforming encoders produce identical bytes for identical input. For
codec 1 streams they produce identical decoded content, identical manifests except for
`bodyDigest` and `compressedLength`, and identical materialised files.

Behaviour IDs for this format are `F1`–`F17` in `docs/test-plan.md`.

### Published record

An `ENTRY` record is the served line with one key added and four metadata fields removed:

- added: `organism` (the organism identifier from the table above), at the top level;
- removed from `metadata`: `versionStatus`, `dataUseTerms`, `dataUseTermsRestrictedUntil`, `dataUseTermsUrl`.

Reasons: `versionStatus` describes the entry relative to later versions and changes when a
revision or revocation is published, so it is recomputed from the record set at recovery
time; `dataUseTerms`, `dataUseTermsRestrictedUntil` and `dataUseTermsUrl` are always the
open-data values for anything eligible for publication and are derived from instance
configuration rather than stored per entry. Everything else, including every pipeline-added
field and `pipelineVersion`, is published exactly as served at first publication.
